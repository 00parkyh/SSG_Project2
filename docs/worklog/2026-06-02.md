```java
@Test
public void concurrentDecreaseWithoutLock_shouldBreakStockConsistency() throws Exception {
    StockFixture fixture = createStockFixture(INITIAL_QUANTITY);

    List<Boolean> results = runConcurrently(CONCURRENT_REQUESTS,
            () -> decreaseWithoutLock(fixture.stockId, REQUEST_QUANTITY, allReadersReady, updateStart));

    int successCount = countSuccess(results);
    int finalQuantity = getStockQuantity(fixture.stockId);

    assertEquals(CONCURRENT_REQUESTS, successCount);
    assertEquals(0, finalQuantity);
    assertFalse(isStockInvariantValid(successCount, finalQuantity));
}
```

```java
@Test
public void concurrentDecreaseWithPessimisticLock_shouldKeepStockConsistency() throws Exception {
    StockFixture fixture = createStockFixture(INITIAL_QUANTITY);

    List<Boolean> results = runConcurrently(CONCURRENT_REQUESTS,
            () -> decreaseWithPessimisticLock(fixture.stockId, REQUEST_QUANTITY));

    int successCount = countSuccess(results);
    int finalQuantity = getStockQuantity(fixture.stockId);

    assertEquals(1, successCount);
    assertEquals(0, finalQuantity);
    assertTrue(isStockInvariantValid(successCount, finalQuantity));
}
```

## 수정 이유

- 초기 재고 100개에 대해 동시에 2개의 100개 차감 요청을 보내는 상황을 재현했다.
- 락이 없으면 두 요청이 모두 같은 초기 재고 100개를 읽고 모두 성공 처리되어, 성공 처리 수량 기준 정합성이 깨진다.
- `FOR UPDATE`를 사용하면 첫 요청만 성공하고 두 번째 요청은 갱신된 재고 0개를 확인해 실패하므로 정합성이 유지된다.
- 따라서 동일 재고 row 차감 로직에는 비관적 락 또는 그에 준하는 원자적 차감 방식이 필요하다는 판단 근거를 확보했다.

```java
    response.sendRedirect(request.getContextPath() + "/login");
    return false;
}
```

## 수정 이유

- 기존에는 세션 체크가 컨트롤러, `ControllerAdvice`, 인터셉터에 분산되어 있어 세션 만료 시 동작이 메뉴마다 달라질 수 있었다.
- MVC 요청 진입 단계에서 인증 여부를 먼저 확인하도록 인터셉터를 명시 등록했다.
- `/login`, 권한별 로그인 페이지, 회원가입, 정적 리소스, 에러 페이지는 세션 없이 접근 가능하도록 예외 처리했다.
- 세션의 `role` 값이 `Role` enum이거나 문자열인 경우를 모두 처리해 캐스팅 예외 가능성을 줄였다.
